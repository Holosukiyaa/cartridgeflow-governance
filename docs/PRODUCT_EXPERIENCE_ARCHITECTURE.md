# CartridgeFlow 产品体验架构

## 一句话定位

意图编排层帮用户发现方向并把想法编排清楚；能力实现层把特殊做法制成可复用小卡带；CartridgeFlow 再把可信小卡带递归组合为完整应用。

## 核心产品模型

> 卡带不只是一条完整流程的最终包，流程内部也由卡带组成。

```text
完整应用卡带
  ├─ 触发能力卡带
  ├─ 信息获取能力卡带
  │   ├─ 原子工具或包自有 DLC
  │   ├─ 标准化子流程
  │   └─ 筛选子流程
  ├─ 内容生成能力卡带
  └─ 交付能力卡带
```

卡带可以封装单个工具，也可以包含完整 Flow，还可以继续依赖其他卡带。嵌套必须透明、可分析、可测试、可版本化、可追溯。最终运行包可以把嵌套物化成一个自包含 Root Flow，但不能丢失每个子卡带的身份、版本和来源。

## 两层产品模型

CartridgeFlow 只保留两个顶层认知与产品边界。方向探索和方案编排是意图编排层中的两种模式，不再被描述为彼此割裂的层级；可执行技术事实属于独立的能力实现层。

```text
意图编排层 Intent Layer
  ├─ 方向探索：帮助用户发现“可以做什么”
  └─ 方案编排：帮助用户说清“每一步要什么”

能力实现层 Capability Layer
  ├─ 实现设计：精确声明“每一步怎么执行”
  ├─ 运行验证：证明成功结果和安全失败
  └─ 版本发布：冻结契约、依赖、证据与来源
```

- 普通用户只使用创作空间，可以从方向探索开始，也可以带着明确目标直接进入方案编排。
- 高级用户可以直接进入能力工坊制作可执行能力。
- 创作空间遇到特殊能力缺口时，只在需要时把该节点带入能力工坊。
- 两个界面由同一个后端和同一个 8765 端口提供，共享事实，不靠跨端口互调。

画布是共同载体，但画布上展示的语言不同：创作空间展示用户目的；能力工坊展示可执行技术 Flow。两个层级不会同时堆在同一个界面上。

## 创作空间：探索并编排目的

用户默认进入一张空画布，表达目标后，AI 生成完整的语义草稿。节点描述“用户要得到什么”，而不是“调用哪个 MCP”。用户先调整整体草稿，再打开某个节点深化字段、审核来源和确认结果。

```text
用户：我想做一份每天早上的 AI 日报

[每天早上开始]
  -> [获取可靠的 AI 信息]
  -> [筛选并生成中文简报]
  -> [交付简报]
```

创作空间先忠实表达需求，再查询可信能力。能力库存不能反过来裁剪用户想法。

每个节点独立解析：

```text
语义节点
  -> 系统可信能力
  -> 组织可信能力
  -> 当前工作区可信能力
  -> 都没有时保留为“待补齐能力”
```

“待补齐能力”不是错误。用户可以继续修改整个链路、确认需求、替换方案或进入高级制作流程；只有真实运行验证和最终打包要求所有必需能力已经解析并审核。

能力匹配本身也必须可审核。AI 可以提议一个已有能力，但用户必须能在原节点判断“这个实现不适合”，并将该精确版本退回为能力缺口。退回不删除全局能力，也不永久屏蔽未来新版本。

创作空间不展示 Root Flow、executor、MCP ID、权限字段、调优版本、固定节点工具栏或运行调试控制。它只展示语义目标、关系、可编辑业务字段、能力来源和审核状态。

## 能力工坊：制造做法

能力工坊保留旧前端最有价值的交互经验：技术配置不脱离链路图，选中节点后就地编辑，不把用户扔进分散的配置文件或独立控制台页面。

高级用户可以：

- 创建、连接、移动和删除技术 Flow 节点；
- 设置节点执行器、动作、效果和参数；
- 声明能力公开输入、公开输出和创作空间可编辑字段；
- 固定依赖的其他能力发布物；
- 检查入口、成功出口、孤立节点和契约边界；
- 将完整 Flow 发布成不可变的工作区可信能力。

“能连到完成节点”不等于可发布。能力成功路径必须执行真实状态；工具或远程节点必须绑定可调用实现；声明的公开输出必须由成功路径显式写出。空 Flow、占位地址、空工具调用和不存在的数据输出全部失败关闭。

从创作空间的能力缺口进入时，目标已经填入新能力上下文。发布后回到创作空间，系统重新匹配原节点并显示能力名称、信任范围和精确版本。用户审核的是“这个实现是否符合我的目的”，而不是重新搭一次技术 Flow。

能力卡带粒度必须保留用户需要审核的语义边界。不能把“触发、采集、生成、发送”整个应用藏成一个万能节点；但一个内部复杂、外部结果明确的特殊能力可以作为一个节点复用。

## 信任不是官方垄断

官方能力只能覆盖常见需求，不能覆盖整个世界。CartridgeFlow 允许用户自己制作能力，同时区分信任范围：

- 系统可信：官方治理并提供；
- 组织可信：组织治理并在组织范围复用；
- 当前工作区可信：用户在本地工坊制作并确认；
- 待验证：AI 生成或刚导入，不能进入最终应用包。

本地工坊不能授予系统或组织信任。AI 可以辅助写 Flow 和测试，但不能自行把候选物变成可信事实。

## 两种打包

“打包”有两个严格区分的含义。

### 能力发布

工坊把一段能力实现 Flow 冻结为不可变的小卡带，记录完整实现、公开契约、精确依赖、权限、证据、来源和摘要，然后发布到能力注册表。它解决“这个语义节点具体怎么做”。

### 项目打包

创作空间将已审核的语义链路和每个节点绑定的小卡带组合为完整应用。它解决“整个项目如何交付”，也是意图编排层唯一进入能力实现层的出口。

```text
校验语义链路与用户审核
  -> 解析精确能力版本
  -> 递归计算依赖闭包
  -> 检查信任、公开端口、权限和文件
  -> 确定性命名空间物化
  -> 合并包自有 DLC
  -> 保留完整来源链
  -> 验证清单并签名
```

未解析、未审核、版本漂移或契约不兼容的必需能力不能进入最终包，但可以长期保留在创作空间草稿中。

## 运行与测试

Desktop Runner 是独立运行壳。它验证候选能力卡带和最终应用卡带能在没有创作空间会话、前端状态或源码工作区依赖的情况下运行。

创作空间不承载生产运行、暂停、历史或调试事件。能力工坊负责技术实现和发布前边界检查，Desktop Runner 负责真实执行并消费签名包。

“打包成功”不是运行证据。一个能力或完整应用只有同时满足以下条件才算闭环：签名包能被独立 Base 激活；真实工具操作完成；声明的数据链没有断裂；主要输出非空；交付状态为 `delivered`；无效输入沿声明失败路径关闭并保留原始错误节点。跨仓最小验收入口由治理仓的 `scripts/check_handoff_e2e.py` 统一调用产品工作台和 Desktop Runner。

创作空间对来源的审核和冻结可以成为只读能力的运行授权事实，但授权只覆盖打包时固定的业务字段。Base 的通用 broker 仍负责 HTTPS、公开地址、响应大小、超时和声明能力检查；能力卡带负责 RSS 等领域解析，不能把领域实现塞回 Base。

## 体验契约

1. 用户想法不向当前适配器库存妥协。
2. 缺少实现时保留原语义节点，不伪造可执行性，也不拒绝整个想法。
3. 普通用户编排目的，高级用户可以完整控制实现。
4. 所有关键工作都围绕画布完成，但不同层级不在同一界面混杂。
5. 发布新能力后重新解析原节点，不让用户在工程间反复重建上下文。
6. 卡带既是完整应用，也是内部可复用能力。
7. Base 保持通用，领域能力属于卡带及其 DLC。
8. 打包负责严格组合，不负责猜测未确认的能力实现事实。
9. 创作空间、能力工坊和 demos 分别承担语义创作、能力制造和运行验证。
10. 签名、导入、真实执行、非空输出、数据链、交付和失败路径必须作为一组验收，缺一项都不能称为闭环。
11. AI 能力匹配是可拒绝提议；用户拒绝后保留节点和需求，不让同一发布摘要自动绑回。
12. 工作区可信发布必须证明可执行契约完整，不能把空 Flow 或占位节点包装成可信能力。
