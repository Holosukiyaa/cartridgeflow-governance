# AI 责任路由覆盖与当前差距

> 状态：设计决定与整改基线
>
> 记录时间：2026-08-11
>
> 适用范围：`CartridgeFlow-governance` 对 CartridgeFlow 与 Desktop Runner 的外置治理

## 1. 目的

外挂治理的首要目标不是成为一个理解并控制所有楼层的中央总管，而是让 AI 更快、更准确、更可追溯地完成工程工作。

它需要回答以下问题：

1. 这次任务首先应该进入哪个楼层、哪张知识卡和哪些代码文件？
2. 修改是否跨越了边界，因而需要同时检查生产者和消费者？
3. 哪些产品原生检查必须运行，哪些检查可以根据明确作用域缩小？
4. 失败后应定位到哪个责任区域、哪次路由决定、哪项检查和哪次知识同步？

外挂治理不负责替代产品协议、源代码和产品原生测试。即使整个治理仓库被移除，产品与 DR 仍必须能够构建、启动、运行和交付。

本设计以四条原则为主线：

> 卡片无历史，审计有事件。
>
> 全局目录不等于全局失效域。
>
> 静态通过不等于产品通过。
>
> 不确定性只能扩大验证范围。

## 2. 已确认的设计思想

### 2.1 多个自治小项目，而不是一个中央知识模型

每个楼层和知识卡只负责自己的精确区域。它们可以独立演进，不要求其他楼层、父卡片或全局目录跟随升版。

整体知识在任意时刻都可能存在不同程度的时间差。这种漂移是多个自治区域并行演进的正常状态，不是必须被消灭的异常。

治理要做的是限制漂移的影响范围，并保证它最终收敛：

```text
任务或故障
  -> 定位主要楼层与知识卡
  -> 阅读真实代码、合同和测试
  -> 修改代码
  -> 运行独立于外挂治理的产品验证
  -> 必要时后同步所属知识卡的当前内容
  -> 在独立 Ledger 中记录路由、修改、检查和知识同步事件
```

### 2.2 事实权威顺序

当前产品实际锁定、经过验证并由当前实现消费的外部合同，定义产品必须保持的外部行为。源码、运行事实和产品原生测试描述当前实现实际上做了什么。两者冲突时必须产生阻断诊断，不能用简单优先级把冲突抹掉。

查找事实时按以下顺序收集证据：

1. 当前实际锁定、验证通过且由当前实现消费的外部合同；
2. 当前源代码、运行事实和产品原生测试；
3. Floor 与 Boundary 卡片声明的责任和正式关系；
4. Knowledge 卡片保存的当前局部理解；
5. 生成索引、检索结果和 AI 推断。

未锁定的未来协议、旧代际合同和内部知识合同不能仅凭“位于产品协议库”就凌驾当前实现。Knowledge 卡片是面向施工的局部投影；它可以暂时过时，但不能覆盖合同和代码事实，冲突还必须保持可见并触发同步责任。

### 2.3 卡片无历史，审计有事件

知识卡正文只描述当前有效的目的、概念、代码导航、工作方式和陷阱，不应混入时间线、工作日志或过期做法。

Knowledge 卡本身只保存当前局部理解，必须保持以下约束：

- `revision = NULL`；
- 不进入 `card_revision`；
- 不拥有规范规则和检查器绑定；
- 只解释一个 Floor，并保持精确作用域；
- 默认任务上下文不加载任何历史事件。

知识变化的可追溯性由独立的 `knowledge_sync_event` 提供，而不是由 `knowledge_revision` 或卡片正文提供。同步事件至少回答：

- 哪次代码变化触发了同步；
- 修改前后的内容摘要；
- 当时涉及的代码和合同；
- 运行了哪些验证；
- 哪次路由决定或故障暴露了知识差距。

同步事件不改变 Knowledge 的描述性权威，不使其获得版本谱系，也不应导致父卡片、相邻卡片或无关区域的检查证据失效。

## 3. 责任路由覆盖

### 3.1 定义

责任路由覆盖是指每个受治理代码事实都能被稳定地路由到：

- 一个主要 Floor 所有者；
- 零个或多个精确作用域的 Knowledge 卡片；
- 必要的显式 `depends_on` 关系；
- 当生产者和消费者同时参与，或公开合同变化命中绑定时，对应的 Boundary 卡片；
- 与这些责任区域绑定的检查器和失败责任。

责任路由覆盖衡量的是“AI 是否知道去哪里工作、还需要找谁、应运行什么”，不是“系统行为已经被证明正确”。

### 3.2 必须区分的五种验收状态

| 状态 | 证明内容 | 不证明什么 |
| --- | --- | --- |
| 静态检查 | 文件具有唯一主要楼层，知识作用域可定位，依赖、引用和合同绑定可解析 | 代码行为正确或两端行为等价 |
| 楼层验证 | 产品或 DR 的原生测试与构建通过 | 跨仓库交付成功 |
| 边界验证 | 生产者和消费者对载荷、错误、升级与回滚具有一致解释 | 完整用户链路已经成功 |
| 场景验收 | 真实生产者到消费者链路及关键失败路径通过 | 所有未来输入和环境都正确 |
| 完整验收 | 前四类状态都具有针对当前依赖足迹的新鲜证据 | 未被声明或未知的未来风险不存在 |

只有前四类状态都具有当前证据时，才可以称为“完整治理验收通过”。单纯的索引无发现只能称为“静态检查通过”。浏览器和 CLI 必须分别显示五种状态，不得用一个绿色结果代替它们。

### 3.3 保守路由原则

治理可以帮助缩短 AI 上下文和减少无关检查，但不能因为知识缺失、过时或冲突而静默跳过产品原生验收。

| 路由状态 | 必须采取的动作 |
| --- | --- |
| 唯一且新鲜 | 运行精确卡片检查及相关产品原生检查 |
| 存在多个可能所有者 | 扩大到所有候选楼层，不允许任选其一 |
| 没有所有者或知识卡冲突 | 回退到目标仓库完整检查并产生路由诊断 |
| 跨越 Floor | 同时加载生产者、消费者和参与边界 |
| 修改公开合同 | 从合同绑定反向定位 Boundary，主动展开生产者、消费者和真实场景检查 |
| Knowledge 与代码冲突 | 以当前合同和代码事实为准，任务结束前同步知识并写入外部同步事件 |

不确定性只能扩大验证范围，不能缩小验证范围。

责任路由必须同时支持两个入口：

```text
代码路径 -> Floor / Knowledge
合同变化 -> Contract Binding -> Boundary
Boundary -> Producer + Consumer + Scenario
```

公开合同变化不能等待生产者和消费者恰好同时进入上下文。Boundary 是主动扩展责任闭包的路由节点，不只是两个已选楼层之间的被动说明。

## 4. 责任追踪模型

“追责”应首先追踪到工程责任和决策链，而不是简单归咎于个人。

一次可追踪的 AI 施工至少应关联：

```text
task/run id
  -> 输入目标与路径
  -> 路由到的 Floor / Knowledge / Boundary
  -> 路由原因和当时的卡片摘要
  -> 实际修改的代码与合同
  -> 运行的检查器及未运行原因
  -> 检查证据和失败规则
  -> 知识同步事件
```

责任追踪采用三库分离：

| 数据库 | 保存内容 | 生命周期 |
| --- | --- | --- |
| `governance-source.sqlite` | 当前责任模型、卡片、规范规则和正式关系 | 人工审核与原子发布 |
| `governance-index.sqlite` | 可以从当前目标重新扫描得到的代码、符号、依赖、合同和覆盖事实 | 可丢弃并重建 |
| `governance-ledger.sqlite` | 不能因索引重建而丢失的路由、检查计划、检查结果和知识同步事件 | 追加写入与独立校验 |

Ledger 不成为产品依赖，也不成为卡片正文来源。AI 的默认施工上下文只读取当前卡片和当前索引；只有审计、故障分析或新鲜度判断才查询 Ledger。

一次证据的精确依赖足迹至少包括：

- 实际读取的卡片 ID 与内容摘要；
- 实际命中的 scope 与使用的 relation 摘要；
- 代码 artifact 与内容摘要；
- 产品合同版本与内容摘要；
- 检查器与检查器摘要；
- 路由算法或上下文编译器摘要；
- 目标配置摘要；
- 被选择的卡片闭包和检查计划摘要。

精确足迹不仅说明“读取了什么”，还必须重建“为什么选择这些责任区域，以及为什么没有选择其他楼层”。在精确依赖追踪完成前，全局摘要继续作为保守失效条件；完成后，全局摘要只证明数据库完整性，不再自动使所有自治区域的证据失效。

失败后应能区分：

- 代码实现错误；
- 产品原生测试缺失；
- 责任作用域错误；
- 知识卡过时；
- 路由算法错误；
- 检查选择过窄；
- 边界或合同本身不完整。

## 5. 实现状态与剩余缺口

### 5.1 独立、持久的治理 Ledger 已实现

`governance-ledger.sqlite` 已与权威源和可重建索引分离。路由运行、检查计划、规则结果、诊断、五态验收和知识同步事件只追加写入 Ledger；UPDATE 和 DELETE 由数据库触发器拒绝。重建 `governance-index.sqlite` 不会改动 Ledger。

`knowledge` 和 `task` 的 `revision` 仍为 `NULL`，验证器继续拒绝它们进入 `card_revision`。知识变化由外部 `knowledge_sync_event` 审计，不把时间线写回 Knowledge 正文。

知识同步事件保存：

```text
event_id
event_schema
card_id
floor_card_id
before_digest
after_digest
source_refs
trigger_kind
trigger_reference
changed_paths
verification_run_ids
route_run_id
occurred_at
reason
actor
content_digest
```

Ledger v2 可原位读取并迁移 v1 事件。迁移只增加事件结构和关联字段，不重写既有事件的内容摘要；新旧事件按各自的事件 schema 独立验签。

### 5.2 五种验收状态已拆分

索引命令现在只报告 `Static governance checks passed`。统一检查入口和浏览器分别展示 `static`、`floor`、`boundary`、`scenario` 和 `complete`；局部运行把未执行维度标为 `not-run`，只有无作用域的全量运行才计算完整验收。

### 5.3 保守回退、合同反向路由和 Knowledge 事实检测已实现

无归属和歧义输入会进入 `routing.state=conservative`，上下文和检查范围扩大到候选目标楼层。公开合同输入按 `Contract Binding -> Boundary -> Producer + Consumer + Scenario` 反向展开，并有失败测试覆盖。治理源库检查始终运行。

每个活跃 Knowledge 源码引用现在保存审核时的确定性 artifact 集合摘要。索引重建会把引用标为 `current`、`stale` 或 `unknown`；被选中的 Knowledge 一旦不是 current，路由就进入保守模式并扩大到对应目标的 Floor。`sync_knowledge_anchors.py` 是显式审核和发布动作，不允许扫描器自行接受新摘要。

每张 Knowledge 还必须声明至少一个人工审核的机器事实断言。当前受限判定只允许 `artifact_exists`、`text_contains` 和 `json_pointer_equals`，不执行卡片正文或卡片提供的命令。断言结果进入生成索引的 `knowledge_assertion_status`；`conflict` 产生 error，`unknown` 产生 warning，两者都会使被选中的卡片进入保守路由并扩大到目标 Floor。规则和检查器仍由 `constitution.project` 所有，Knowledge 保持描述性且不拥有治理规则。

这不等于通用自然语言理解。来源锚负责发现“依据变了”，事实断言负责核验少量关键语义，其余正文仍需代码审查、产品测试或专门领域检查器证明。

### 5.4 产品正式验收已接入，并暴露当前协议锁 blocker

`check.product.formal` 独立运行产品自身要求的两个正式入口：

```powershell
python scripts/run_conformance.py --quiet
python scripts/audit_protocol_governance.py
```

两个命令即使前一个失败也都会执行，任一失败都会阻断 floor 和 complete。当前权威协议源已经形成 clean-v1 四层 75 合同候选，产品也有四层投影与 clean Base 候选；但源提交尚未发布，嵌入式产品 Registry、v3 锁和正式 Base 仍属于 unified-v1。治理必须继续把这种不一致报告为 blocker，不能用本地候选证据冒充正式切换。

### 5.5 Boundary 检查仍需逐条增加行为证据

当前边界检查能证明生产者、消费者、接口声明、合同绑定和楼层检查器存在，但不能单独证明：

- 两端对同一载荷具有相同解释；
- 请求、响应和错误码一致；
- 升级、失败和回滚语义一致；
- 跨 Python 与 Go 的兼容性结论一致。

工作台到 DR 的安装交界已有跨语言行为证据；其余关键 Boundary 仍需要真实契约测试或跨仓库场景，不能只依赖关系元数据。

### 5.6 工作台到 DR 已升级为 CF-CRE@2 + clean-v1 真实场景

场景现在由真实 Workbench API 创建、保存、调优、验证和认证 Flow，再用现有产品 CF-CRE@2 构建器生成签名包。产品 clean Distribution 投影器从临时 v4 Registry 生成 installation request/plan，DR 的真实 Go Store 完成验签、物化和激活并返回 installation result；成功与篡改失败结果都由产品 clean Schema 反向验证。随后 DR 完成公开设置读取与保存、必需输入拒绝和成功交付，篡改失败不得改变活动卡带。

当前 Workbench 包装 API 仍硬编码 CF-CRE@1，因此场景明确记录其实际打包入口为 `core.protocol.build_release_archive`，不伪称工作台包装 API 已支持 v2。clean Base 也仍是候选而非正式活动清单。

同一真实包现在携带非空被动 UI 资产和 `local_resource` 能力声明。DR 从安装后的包提供 UI，并把 `document_lookup` 资源角色解析到宿主注入的 `remote_api` 连接；流程实际调用临时 HTTP 资源并把返回值交付。清单能力来源、流程传输类型和宿主连接三层分别验证，不再用认证警告或 mock 结果代替运行证据。

### 5.7 责任路由核心失败路径和 Knowledge 来源漂移已有测试

治理测试已经覆盖：

- 无归属和歧义触发保守回退；
- 公开合同反向展开 Boundary、生产者、消费者和 Scenario；
- Ledger UPDATE/DELETE 被拒绝，索引重建不改写 Ledger；
- 无关 Knowledge 变化只使真正依赖它的证据过期；
- Knowledge 来源摘要失配会产生 warning、标记 stale，并把验证扩大到所属目标 Floor；
- Knowledge 关键事实冲突会产生 error、标记 conflict，并把验证扩大到所属目标 Floor；
- Knowledge 锚点同步是幂等的，旧 Ledger 事件迁移后仍保持原始摘要有效；
- 产品正式验收适配器即使遇到首个失败仍执行全部入口。

未结构化的自然语言正文仍不能由通用扫描器判真；新增领域必须先选择稳定关键事实，再增加受限断言或专门产品检查器。

### 5.8 权威发布和仓库状态尚不可复现

治理仓库已建立可审阅 Git 基线。clean 产品投影和 DR clean 消费者分别具有目标仓提交，但 CartridgeFlow 仍存在其他工作区变化，DR 仍是 CartridgeFlow 目录中的独立嵌套仓库，协议源提交也尚未发布；这些目标仓库状态不能由治理数据库替代。

数据库摘要可以证明某个文件内容没有变化，但不能替代代码、检查器、目标配置和数据库发布物的可审阅 Git 历史。

### 5.9 完整验收已包含产品协议锁一致性

产品协议锁审计和完整 conformance 现在属于 blocker 级 `floor` 验收。当前不一致会明确形成失败证据，并使 `complete` 失败；静态无 finding 不再能覆盖它。

### 5.10 全局目录已不再形成普通证据的全局失效域

普通楼层、边界和场景证据按实际卡片、scope、relation、artifact、合同、检查器、路由器、上下文编译器、目标配置、卡片闭包和检查计划逐项判断。修改一张无关 Knowledge 不会使其他自治区域的证据过期。

全局源摘要只绑定源库完整性检查，全局事实摘要只绑定索引完整性检查。这两个摘要保护数据库完整性，不参与普通自治区域证据的新鲜度。

## 6. 目标工作流

### 6.1 修改前

1. 以精确路径、符号、API 或发行物确定主要 Floor。
2. 加载该 Floor 下作用域命中的 Knowledge 卡片。
3. 沿显式依赖补齐所依赖的 Floor。
4. 若输入包含公开合同变化，从 Contract Binding 反向定位 Boundary，并主动展开生产者、消费者和 Scenario。
5. 对普通代码任务，生产者和消费者都参与时加入对应 Boundary。
6. 若归属缺失、歧义或冲突，停止精确裁剪并扩大检查范围。

### 6.2 修改中

1. Knowledge 负责导航，不代替阅读真实代码和合同。
2. 不越过未声明的责任边界修改其他楼层。
3. 必须跨楼层时，把相关 Floor 和 Boundary 纳入同一个任务记录。
4. 对公开合同的修改同时维护生产者、消费者和场景夹具。

### 6.3 修改后

1. 运行受影响区域的产品原生测试。
2. 在不确定、冲突或公共合同变更时扩大验证范围。
3. 运行适用的 Boundary 和 Scenario 检查。
4. 同步确实受到代码变化影响的 Knowledge 卡片。
5. 为每张变化的知识卡向 Ledger 单独追加 `knowledge_sync_event`。
6. 将精确依赖足迹、检查计划、检查结果和未运行原因写入 Ledger。

## 7. 不变量

后续实现必须保持以下不变量：

1. 产品和 DR 不得依赖外挂治理才能构建或运行。
2. 当前锁定且验证通过的外部合同、当前代码事实和产品原生测试始终高于 Knowledge 卡片；它们彼此冲突时必须阻断而不是静默覆盖。
3. 每个受治理文件必须有且只有一个主要 Floor 所有者。
4. Knowledge 卡片只解释一个 Floor，并保持精确作用域。
5. Knowledge 可以暂时过时，但冲突必须可见并最终同步。
6. Knowledge 卡片无历史；每次知识变化独立产生同步事件，不连带版本化其他卡片。
7. 不确定性只能扩大上下文和检查范围。
8. 公开合同变化必须同时验证生产者和消费者。
9. 静态无 finding 不得被表述为完整产品验收通过。
10. 每次 AI 修改必须能回溯到路由决定、代码差异、检查证据和知识同步。
11. 全局目录用于发现和组合责任，不得天然成为所有自治区域的共同失效域。

## 8. 整改优先级

以下顺序是依赖顺序，不得因为后续功能更显眼而跳过前面的假绿修复。

### P0-1：接入产品正式验收（已完成）

- 将产品正式协议审计和完整 conformance 接入产品楼层检查器。
- 产品协议锁失配必须成为完整验收 blocker。
- 产品正式全量入口不依赖卡片选择；精确路由只能增加局部快速反馈，不能代替它。

### P0-2：拆分验收状态（已完成）

- 将静态检查、楼层验证、边界验证、场景验收和完整验收分开展示。
- 修改索引 CLI 的通过措辞，禁止把静态无 finding 表述为完整通过。
- 完整验收只聚合当前且满足依赖足迹的下层证据。

### P0-3：实现保守回退与合同反向路由（已完成）

- 已为无归属、歧义和 Knowledge 来源漂移扩大候选楼层或目标仓库检查。
- 实现 `Contract Binding -> Boundary -> Producer + Consumer + Scenario`。
- 为检查选择、回退策略、Knowledge 来源漂移和公开合同闭包增加失败测试。

### P0-4：增加独立 Ledger 与精确证据足迹（已完成）

- 新建与权威源、生成索引分离的 `governance-ledger.sqlite`。
- 追加保存路由运行、检查计划、未运行原因、检查证据和 `knowledge_sync_event`。
- 在精确足迹完成前保留全局摘要的保守失效；完成后将新鲜度收窄到真实依赖。
- 保持 Knowledge 正文只描述当前状态，并继续禁止 Knowledge 进入 `card_revision`。

### P1-5：补强 CF-CRE@2 与 clean-v1 真实边界（首个场景完成）

- 已增加 CF-CRE@2 公共设置的工作台到 DR 场景，并覆盖 clean 安装 request/plan/result 的 Python-Go 等价性、成功和篡改失败。
- 已覆盖非空被动 UI 的宿主提供，以及 `local_resource` 角色到 `remote_api` 连接的实际解析和调用。
- 为其他关键跨语言合同继续增加生产者/消费者等价性测试。
- 明确每个 Boundary 的行为证据，而不仅是结构绑定。

### P1：建立可复现发布基线

- 保持治理测试全部通过，并为新增路由行为补充自包含失败测试。
- 建立治理仓库首个可审阅提交和数据库发布基线。
- 明确 CartridgeFlow、协议源和 DR 本地状态的仓库边界与引用方式。

## 9. 完成标准

责任路由覆盖可以认为达到首个稳定版本，需要同时满足：

- [x] 所有受治理文件具有唯一主要 Floor；
- [x] 无归属和歧义能够触发保守回退；
- [x] Knowledge 来源漂移可检测，并以代码事实优先扩大验证范围；
- [x] Knowledge 的审核关键事实具备受限领域检查器、冲突诊断和保守回退；未结构化正文不伪称可自动判真；
- [x] Knowledge 修改可向独立 Ledger 追加同步事件，卡片本身仍无历史；
- [x] 产品正式验收入口不依赖卡片选择即可运行；
- [x] 静态、楼层、边界、场景和完整验收状态分开展示；
- [x] 产品协议锁失配会成为治理 blocker；
- [x] CF-CRE@2 + clean-v1 安装真实交付场景通过；
- [x] 当前治理测试全部通过；
- [x] 一次 AI 修改可完整回溯到路由、差异、检查计划、检查结果和知识同步事件；
- [x] 无关 Knowledge 变化不会使其他自治区域的精确证据失效。

## 10. 本文不解决的事项

本文不定义新的 CartridgeFlow 产品协议，不决定四层协议的具体合同内容，也不要求全局知识在同一时刻完全一致。

本文只固定外挂治理的责任路由目标、可接受的漂移方式、不可接受的静默漏检，以及当前需要整改的工程差距。
