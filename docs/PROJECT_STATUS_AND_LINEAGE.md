# CartridgeFlow 项目现状与版本谱系

> 状态：项目交界同步说明
>
> 本文记录产品版本、分支归属和后续落地边界。它不是新协议正文，也不向新协议引入旧协议的编号、迁移关系或历史兼容要求。

## 1. 当前结论

CartridgeFlow 的共同根版本是 **v0.6.0**，不是 v0.6.0-SP。

DR 的历史归属也是 v0.6.0。后来从根版本上形成了面向 DR 运行台的 **v0.6.0-SP 特化分支**；当前工作台则继续沿另一条方向演化为 **v0.7.0**，在 v0.6.0 的核心内核之上增加语义层。

因此，当前不是“v0.7 工作台附带一个落后的 DR”，而是同一个 v0.6.0 内核的两条后续分支：

```text
CartridgeFlow v0.6.0
共同根版本 / 核心内核
├── v0.6.0-SP
│   └── 面向 DR 运行台的产品特化
└── v0.7.0
    └── 在 v0.6.0 内核上增加语义层和新的创作体验
```

## 2. 三个版本节点

### 2.1 v0.6.0：共同根版本

v0.6.0 是基础产品和核心内核的版本基线。它建立了卡带、Flow、执行、发布和运行端之间的基本边界，也是后续两个分支共享的技术来源。

这里的“内核”包括可执行 Flow 的基本事实、卡带交付边界，以及工作台向运行端交付卡带的基本方式。

### 2.2 v0.6.0-SP：DR 特化版本

SP 不是根版本，也不代表整个 CartridgeFlow 的通用发展方向。它是围绕 DR 运行台做出的专项特化，重点服务于：

- 单机运行壳和单卡带部署；
- 卡带导入、签名校验、激活、卸载和回滚；
- 运行台设置、用户偏好和本地数据；
- DR 对可执行 Flow、模型、工具和 UI 的能力约束；
- 面向最终用户的独立交付形态。

`C:\_HOLOLAB\code\temp\CartridgeFlow-0.6.0` 是这一代 SP 快照。阅读其中的文档时，需要区分继承自 v0.6.0 的共同能力和为 DR 增加的专项能力。

### 2.3 v0.7.0：语义层扩展版本

v0.7.0 的主要变化是增加语义层和更高层的创作体验，例如 Intent Studio 与 Capability Workshop 的分工、语义节点、能力解析和递归组合。

v0.7.0 并没有替换掉 v0.6.0 的核心内核。它是在原有内核之上增加一层语义表达和创作编排，因此不能把 v0.7.0 视为 SP 的升级版，也不能把 DR 的特化约束直接当成 v0.7 工作台的产品约束。

## 3. DR 的正确定位

DR 在运行时独立于开发工作台，但这种独立是部署和运行时边界上的独立，不是版本血缘上的独立。

可以用下面的方式理解：

```text
v0.6.0 工作台能力 ──┐
                    ├── 卡带 / 发布边界 ──> DR 运行台
v0.6.0 核心内核 ────┘
          │
          ├── v0.6.0-SP：为 DR 做专项特化
          └── v0.7.0：增加语义层和新的工作台体验
```

因此，当前工作区中出现 DR 代码，并不表示 DR 属于当前 v0.7.0 工作台。DR 的原始产品背景和运行假设应优先从 v0.6.0 快照中恢复。

## 4. 当前两条落地线

| 维度 | v0.7.0 工作台线 | v0.6.0-SP / DR 线 |
| --- | --- | --- |
| 版本来源 | v0.6.0 内核的语义层扩展 | v0.6.0 内核的 DR 专项特化 |
| 主要职责 | 语义创作、能力绑定、Flow 生成、校验和打包 | 卡带导入、信任校验、设置、执行、历史和交付 |
| 用户对象 | 创作者、开发者、审核者 | 卡带使用者和运行台管理员 |
| 运行方式 | 开发工作台和服务端 | 独立本地运行壳、单机交付 |
| 迁移重点 | 语义层如何落为可执行卡带事实 | 旧运行约束如何映射到新卡带合同 |

两条线共享的是核心能力和最终交付边界，不共享全部产品界面、生命周期和运行时假设。

## 5. 新协议完成后的落地原则

新协议是两条分支重新接合的合同边界：

```text
v0.7.0 语义层
    ↓ 生成 / 展开
新协议与卡带合同
    ↓ 校验 / 导入
DR 运行台（v0.6.0-SP 特化能力）
```

后续实现应分别完成：

1. 工作台侧：按新协议创作、校验、生成和打包卡带。
2. DR 侧：按新协议导入、再次校验、加载设置并执行卡带。
3. 交界测试：用真实打包物验证工作台到 DR 的完整交付路径。
4. 内核复用：优先复用 v0.6.0 的稳定执行事实，避免把 SP 专项逻辑扩散到语义层。

旧的 v0.6.0、v0.6.0-SP 和协议文档可以用于恢复业务行为、运行限制和安全边界，但不能作为新协议的身份、编号或迁移内容来源。

## 6. 必须保持的版本区分

项目中至少存在以下不同的版本轴，不能混用：

1. **产品版本**：v0.6.0、v0.6.0-SP、v0.7.0。
2. **分支/特化关系**：根版本、DR 专项特化、语义层扩展。
3. **协议版本**：新协议自身的独立发布版本。
4. **实现版本**：DR 运行台、工作台、打包器和其他组件各自的实现版本。

产品版本号中的 `0.6.0` 不等于某个协议的 `0.6`；SP 也不应被写成新的共同根版本。
